# Milestone 2026-08-17：打通 LIBERO-PRO 复现与评测闭环

## 一句话总结

这一阶段最重要的成果，不是把某个任务的成功率刷到很高，而是把 CaP-X 在现有算力和模型服务上的完整链路真正跑通了：**模型能生成代码，机器人能执行，系统能多轮观察和修改代码，批量任务能运行，失败过程也能用代码、提示词、图片和视频复盘。**

简单说，我们已经从“理论上能跑”走到了“可以批量跑、可以量化、可以定位问题”。当前系统距离稳定完成复杂操作还有明显差距，但已经有了一个可信的工程起点和实验基线。

## 这段时间完成了什么

### 1. 把模型调用改造成更适合本地和远端复现的版本

主要改动在 `capx/llm/client.py` 和 `capx/integrations/vision/molmo.py`。

完成的工作包括：

- 接入更多实际部署中使用的模型名称，包括 Qwen、DeepSeek、Gemma 和 GPT 的不同服务端命名；
- 同时兼容普通字符串、列表形式的模型回复，以及正文中带 `<think>...</think>` 的推理模型回复；
- 流式和非流式接口都能保留正文与 reasoning；
- 遇到上下文长度超限时，尝试自动缩小输出 token 数并重试；
- 将模型请求超时从 200 秒放宽到 1,200 秒，适应较慢的长推理服务；
- 支持按“命令行显式传入、`CAPX_API_KEY`、用户配置文件、`OPENAI_API_KEY`”的顺序寻找密钥；
- 将 Molmo 指向实际可用的远端 vLLM 服务，并使用服务端注册的模型 ID。

通俗地说，原来的客户端更像是“适配标准接口”，现在则更能容忍不同推理服务在回复格式、鉴权方式、速度和模型命名上的差异。

### 2. 补齐 LIBERO 批量评测入口

主要改动在 `capx/envs/scripts/run_libero_batch.py`。

现在批量入口可以：

- 用 `task_ids` 只运行指定任务，不必每次把整个 suite 全跑一遍；
- 分别配置代码模型和视觉差分模型；
- 把多模型、并行 ensemble、视觉差分等参数完整传给已有的评测框架；
- 检查任务编号是否越界；
- 在启动前检查 YAML 是否真的是合法配置，并确认 `env.cfg` 存在；
- 在配置文件无法创建或写入时记录失败，并继续处理其他任务。

需要强调：多轮视觉差分和 ensemble 能力在 `main` 中已经存在。
本分支做的是**把这些已有能力真正接到 LIBERO 批处理入口上，
并适配当前实验环境**，不是重新发明一套 ensemble 算法。

### 3. 让长时间机器人任务不容易被误杀

主要改动在 `capx/envs/runner.py` 和 `capx/envs/trial.py`。

- 单次 trial 超时从 1,000 秒提高到 10,000 秒；
- 环境 reset 完成后重新开始计算执行超时，避免场景加载或 JIT 编译提前吃掉任务预算；
- LIBERO 任务目标从使用整段 `str.format(...)`，改为只替换精确的 `{libero_environment_goal}` 占位符，避免提示词中其他花括号被误解析。

这解决的是一类很实际的问题：任务并不是不会做，而是可能在模型慢、场景初始化慢或提示词包含代码结构时，先被框架本身中断。

### 4. 把机器人 API 的“使用说明”说清楚

主要改动在：

- `capx/integrations/franka/libero.py`
- `capx/integrations/franka/libero_privileged.py`
- `capx/integrations/franka/libero_reduced.py`

这部分多数不是修改底层控制算法，而是修正和补全会直接展示给代码模型的 API 文档：

- `robot_joint_pos` 实际是 8 维：前 7 维是机械臂关节，最后 1 维是夹爪状态；
- `plan_grasp` 返回的是相机坐标系中的夹爪 TCP 候选位姿，并且已经带有沿抓取局部 `+Z` 方向的 0.12 米偏移；
- 调用者只应做一次相机到世界坐标系的转换，不应再重复添加 TCP 或夹爪长度偏移；
- `solve_ik` 接收世界坐标系中的 TCP 目标，并在内部换算成 `panda_hand` 的 IK 目标；
- `goto_pose(..., z_approach=...)` 的接近方向是世界坐标系 `+Z`，不是夹爪局部 `Z`。

这件事很关键，因为这些 docstring 就是代码模型看到的“工具说明书”。说明书含糊时，模型很容易重复做坐标变换、重复加偏移，或者沿错误方向接近物体。

## 实验结果

以下数字以每个任务目录中的 `summaries.txt` 为准。不能直接数 `trial_*` 文件夹，因为归档保留了重试和中间状态，同一个 trial 编号有时会对应多个目录。

| task_id | 任务 | 有效 trial | 完成次数 | 成功率 |
| ---: | --- | ---: | ---: | ---: |
| 0 | 打开柜子的中层抽屉 | 10 | 0 | 0% |
| 1 | 把碗放到炉子上 | 10 | 1 | 10% |
| 2 | 把酒瓶放到柜顶 | 10 | 1 | 10% |
| 3 | 打开顶层抽屉并把碗放进去 | 9 | 0 | 0% |
| 4 | 把碗放到柜顶 | 10 | 1 | 10% |
| 5 | 把盘子推到炉子前方 | 10 | 0 | 0% |
| 6 | 把奶油奶酪放进碗里 | 10 | 0 | 0% |
| 7 | 打开炉灶 | 10 | 5 | 50% |
| 8 | 把碗放到盘子上 | 10 | 6 | 60% |
| 9 | 把酒瓶放到架子上 | 10 | 0 | 0% |
| **合计** | **10 个任务** | **99** | **14** | **14.14%** |

几个值得注意的现象：

1. 汇总字段中的代码生成/执行成功率约为 `96/99 = 96.97%`，但真正完成任务的只有 `14/99 = 14.14%`。这说明主要问题已经不只是“代码能不能运行”，而是“代码运行后能不能把物理任务做对”。
2. 成功主要集中在“把碗放到盘子上”和“打开炉灶”，两项贡献了 14 次成功中的 11 次。
3. 10 类任务中有 5 类至少成功过一次，另外 5 类仍然是 0%。
4. 每个 trial 平均产生约 6.95 个代码块、约 5.95 次 regeneration。多轮修改确实被大量使用，但许多修改还没有转化成最终成功。

因此，这批结果更适合作为一个**端到端基线**，而不是一个已经成熟的 benchmark 成绩。

## 失败主要卡在哪里

该归档里的 `fail reason.png` 将失败主因归纳成五类：

1. SAM3/Molmo 对源物体、目标或 affordance 的定位错误；
2. GraspNet、抓取动作或接触几何失败；
3. API 选择、调用、数据契约或生成代码错误；
4. 任务规划、动作顺序或预算管理错误；
5. 目标区域判断，以及放置、释放或推动终点错误。

图中没有给出每一类的数量或占比，所以这里不能据此判断哪一类一定最多。它更像是一张后续排查地图：感知、抓取、API 使用、长程规划和最后一厘米的放置都可能成为整条链路的瓶颈。

## 这次 milestone 的实际意义

如果用最通俗的话概括：

> `main` 给了一个完整框架；`Reproduce` 把它接到了当前真实可用的模型
> 和视觉服务上，补齐了批量运行与兼容性问题，并用 99 次正式汇总的
> trial 证明了这条链路确实可以端到端工作。

因此，本阶段已经做到：

- **可跑**：模型、视觉服务、机器人环境和控制 API 能连起来；
- **可批量**：能按 suite、任务和模型组织实验；
- **可量化**：有逐任务成功率，而不是只看个别演示；
- **可复盘**：保留了代码、模型回复、逐轮视觉反馈和视频；
- **可定位**：已经开始把失败拆成感知、抓取、API、规划和落点等环节。

但还没有做到：

- 在 10 类任务上稳定成功；
- 用一个干净、锁定的提交完全复现实验；
- 把当前面向特定服务器的默认配置整理成通用配置；
- 用自动化测试覆盖新增的模型兼容和批处理逻辑。

所以，这更准确地说是一个**工程闭环与实验基线 milestone**，而不是最终性能 milestone。

## 数据口径与已知限制

为了避免过度解读，这批结果有以下限制：

1. 各任务 summary 记录的运行版本是 `7428f9b (Dirty: True)`，不是一个干净工作区；仅凭 Git 提交无法 100% 还原当时的实际代码。
2. 产物由后续提交 `f2a762f` 归档，而分支最后又在 `74d1c7b` 更新了代码和 API 文档。因此不能把归档结果归因于最后一次 API 文档修正。
3. task 3 只有 9 个有效 trial，所以总分母是 99，不是 100。
4. 归档 YAML 中仍写着 `trials: 50`，但实际 summary 每个任务只有 9 或
   10 个 trial；结果必须以 summary 为准，不能称为“每任务 50 次完整评测”。
5. 同一 trial 可能保留多个失败、重试或成功目录，所以不能按目录数量重新计算成功率。
6. 归档实验使用 Qwen3.5；当前 `Reproduce` 批处理入口的默认代码模型已经改成 DeepSeek。两者不能混为同一组结果。
7. 分支没有提交针对密钥优先级、reasoning 解析、上下文超限重试、task ID 筛选和 goal 替换的新测试。
8. 当前默认服务地址绑定特定远端环境，离开对应网络后不能直接使用。
9. 分支删除了 `docs/behavior-tasks.md` 和 `docs/rl-training.md`，但 README 仍然链接它们；合并前需要确认是否有意删除并修复链接。
10. 约 650 MiB 的运行产物直接进入 Git，方便复盘，但会增加仓库体积，后续更适合放到独立实验存储中。

## 下一步建议

优先级可以按下面的顺序推进：

1. **先做一次干净复跑**：锁定代码提交、模型版本、配置和随机种子，补齐为 10 个任务各 10 次，并让归档配置与实际 trial 数一致。
2. **做分环节对照实验**：分别替换感知、抓取、API 说明和规划策略，确认成功率到底卡在哪一层，而不是一次同时改很多东西。
3. **补自动化测试**：覆盖模型回复解析、token 自动调整、密钥来源、任务筛选和 LIBERO goal 注入。
4. **整理可移植配置**：把远端地址和模型 ID 移到环境变量或 YAML 中，不再把特定服务器设成代码默认值。
5. **优先攻克 0% 任务**：先从抽屉、推盘子、物体入容器和酒瓶上架中各选一个，利用现有视频与逐轮代码做针对性修复。
6. **整理实验资产**：Git 中保留 summary、配置和少量代表性案例，大体积视频与完整轨迹迁移到对象存储或 release artifact。
